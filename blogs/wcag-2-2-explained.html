WCAG 2.2 Explained for UI/UX Designers

A practical guide to designing interfaces that are more perceivable, operable, understandable and robust.

    Back to writing

    Accessibility is not a polish step added after a product is designed. It is part of the experience itself. For UI/UX designers, WCAG 2.2 provides a practical framework for thinking about how people perceive, navigate, understand and interact with digital products.

    WCAG stands for Web Content Accessibility Guidelines. WCAG 2.2 became a W3C Recommendation on October 5, 2023. It adds nine success criteria to WCAG 2.1 while keeping the earlier criteria broadly backward compatible.

    What is WCAG 2.2?

    WCAG is an international accessibility standard developed through the W3C Web Accessibility Initiative. It is organized around four principles, commonly remembered as POUR:

    • Perceivable — information can be perceived through different senses and assistive technologies.
    • Operable — people can navigate and operate the interface using different input methods.
    • Understandable — content and interactions are clear and predictable.
    • Robust — the experience works with current and future user agents and assistive technologies.

    WCAG success criteria have three conformance levels: A, AA and AAA. The success criteria—not individual techniques—are the basis for conformance.

    Why UI/UX designers should care

    Many accessibility problems begin during design: low contrast, unclear hierarchy, weak focus states, tiny targets, confusing forms and interaction patterns that depend on one input method.

    Designer's mindset

    Don't ask only “Can the user complete this task?” Ask “Can people with different abilities perceive, understand and operate this experience?”

    The four principles in everyday design

    1. Perceivable

    Use meaningful text alternatives, captions where needed, sufficient contrast and adaptable layouts. Don't communicate important information through color alone.

    2. Operable

    Design for keyboard use and other input methods. Focus should be visible and important actions should not depend on dragging or mouse-only interaction.

    3. Understandable

    Use clear labels, consistent navigation, predictable interactions and useful error messages. Design the recovery path, not only the happy path.

    4. Robust

    Work with developers to preserve semantic structure and compatibility with browsers, user agents and assistive technologies.

    What is new in WCAG 2.2?

    WCAG 2.2 adds nine success criteria covering areas such as focus visibility, dragging, target size, consistent help, redundant entry, accessible authentication and error prevention.

    Focus Not Obscured & Focus Appearance

    Keyboard focus needs to remain visible, and it should not be completely hidden by author-created content. WCAG 2.2 also adds stronger requirements around the appearance of focus indicators.

    Design takeaway: Test focus against sticky headers, floating toolbars, cookie banners and fixed footers. Include focus as a first-class component state.

    Dragging Movements

    Where dragging is not essential, provide another way to complete the action.

    Design takeaway: Don't make drag-and-drop the only way to reorder, select or manipulate important content.

    Target Size (Minimum)

    Interactive targets need enough size and spacing to reduce accidental activation, particularly on touch devices.

    Design takeaway: Design the full hit area—not just the visible icon.

    Consistent Help

    Repeated help mechanisms should appear in a consistent relative order across pages.

    Design takeaway: Keep chat, contact, help and support mechanisms predictable.

    Accessible Authentication

    Authentication should not unnecessarily depend on a user's ability to remember, transcribe or solve a cognitive test.

    Design takeaway: Support password managers, passkeys, copy/paste-friendly fields and accessible recovery flows.

    Redundant Entry

    When information has already been provided during a process, users should generally not have to enter it again.

    Design takeaway: Prefill known information and let users review or edit it.

    Forms are where accessibility becomes visible

    • Use labels that clearly describe fields.
    • Show errors beside the relevant control and explain how to fix them.
    • Preserve entered information when validation fails where appropriate.
    • Use clear focus order and visible focus states.
    • Never rely on color alone for required or error states.
    • Group related fields with meaningful structure.

    Build accessibility into the design system

    Accessibility becomes easier when it is encoded into reusable components instead of remembered on every screen.

    • Semantic color and contrast rules
    • Keyboard focus and interaction states
    • Minimum interactive target areas
    • Form labels, hints and error patterns
    • Responsive and zoom/reflow behavior
    • Motion and reduced-motion considerations
    • Accessible naming and icon usage

    A practical WCAG workflow

    1. Start with user needs. Consider visual, auditory, physical, speech, cognitive and neurological differences.
    2. Review foundations. Check typography, contrast, spacing, hierarchy and responsive behavior.
    3. Design every important state. Include focus, error, loading, empty, disabled and success states.
    4. Check interaction alternatives. Ask whether critical actions work without mouse-only or drag-only interaction.
    5. Test. Use keyboard navigation, zoom and assistive technologies where possible.
    6. Collaborate. Clarify semantics, focus behavior and implementation constraints with developers.
    7. Iterate. Treat accessibility as ongoing product quality.

    Common mistakes

    • Using color as the only status indicator.
    • Removing focus indicators without a replacement.
    • Using tiny icon-only controls with inadequate target areas.
    • Letting sticky UI cover keyboard focus.
    • Making drag-and-drop the only interaction.
    • Repeating information the user already entered.
    • Designing error states only after the happy path.

    Final thoughts

    WCAG 2.2 is most useful when it becomes part of the design process rather than a document opened at the end of a project.

    Learn the criteria that affect your product, turn recurring requirements into design-system rules, and test the actual experience with different input methods.

    Accessibility is ultimately about removing unnecessary barriers. When designers make that goal part of everyday decision-making, better experiences become the default.
